# 解答欄画像の作成の速さ（計測 2026-10-16）

117人 × 100問 = 約1万1千7百枚（読み込み時に端末が先に作る最初の10問を除くと、約1万5百枚）の作成が、方式ごとに、どれだけかかるか。

## 測り方

- 一時的な計測用の Edge Function を本番のプロジェクトに置き、`generate-answer-cells` と同じ処理（用紙の取得 → JPEG の読み取り → 切り出し → 再圧縮 → 保存）を、DB に触れずに動かした。保存先は、本番とは別の接頭辞（`bench/`）。使い終わって、関数・秘密の値・保存したファイル（1600件）を、すべて消した。
- 呼び出しは、開発者の Mac から。1回の呼び出し＝2人 × 20枚 = 40枚（本番と同じ）。ごく短い実験（16〜47秒）なので、数字には、±2割ほどのぶれがある。
- 端末（ブラウザ）側は、Chrome で、切り出しと再圧縮だけを測った（保存の通信は、サーバー側の数字からの推定）。

## わかったこと

- 1回の呼び出し（40枚）は、約 5〜7 秒。用紙の取得 0.5〜1.1 秒、JPEG の読み取り 0.09 秒、切り出しと再圧縮 0.5 秒（1枚 約 25 ミリ秒）、保存（通信）が、残りの大半。**保存の通信を待つ時間が、ほとんど。CPU ではない。**
- 流れ（同時に呼ぶ数）を増やすと、ほぼ比例して速くなる（1本 約 400枚/分）。
- 1回の呼び出しの中で、仕事を詰めすぎると、サーバー関数の上限に当たる（2人 × 25枚 × 4用紙を並列で、HTTP 546）。1回あたり、CPU は 約 1.2 秒で、上限（約 2 秒）に近い。
- Chrome での切り出しと再圧縮は、1枚 2〜4 ミリ秒。端末の力は、足りている。端末の限りは、保存の通信。

## 方式ごとの、全件にかかる時間

| 方式 | 速さ | 全件 |
|---|---|---|
| A. 現状（管理者の画面を開いている。流れ4本） | 1,628枚/分（実測） | 約 7 分 |
| A. 現状（画面を閉じた。定期実行のみ） | 最大 800枚/分（計算。1分に最大20回の呼び出し × 40枚） | 約 15 分 |
| B. サーバーだけ（ブラウザの道を止める） | A と同じ。重なりと記録の上書きがなくなる | 同上 |
| C. サーバー＋管理者の端末（印を共有） | 端末1台 約 300枚/分（推定）。管理者2人で、約 2,200枚/分 | 約 5 分 |
| D. 流れを8本 | 3,035枚/分（実測） | 約 4 分（定期実行のみなら 1,600枚/分の計算で 約 7 分） |
| D. 流れを16本 | 7,071枚/分（実測。短い実験） | 約 2 分（定期実行のみなら 3,200枚/分の計算で 約 4 分） |
| E. 1回の呼び出しの中も並列（保存を20並列・用紙も並列）、流れ4本 | 2,472枚/分（実測。1件失敗） | 約 5 分 |
| E. 同、流れ8本 | 6,007枚/分（実測） | 約 2 分 |
| E. 同、流れ16本 | 5,248枚/分（失敗5件）。上限の付近 | ― |

## 測れなかったもの

- 本番の定期実行そのもの（秘密の値が要る）。計算で出した。
- 管理者が複数人で、同時に画面を開いたときの、重なりと記録の上書き（コードを読んだ推測のみ）。
- 実際の管理者の端末での、保存の速さ。
- 高い負荷での失敗の増え方（流れ16本・E で 0.3%）。失敗した用紙は、30分は取り直されない設計。
