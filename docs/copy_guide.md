# 文言ガイド(草案)

画面・メール・エラー応答の日本語を統一するためのルール。AGENTS.md の用語ルールを前提に、その下位に置く。
調査時点(2026-10-02)の揺れを根拠にしている。実装前にレビューすること。

## 1. 文体

- 丁寧語(です・ます調)で統一する。体言止めは見出し・ラベル・ボタンに限る。
- 1文は短く。エラーは「何が起きたか。次に何をすればよいか。」の2文を基本にする。
- 句読点は全角(。、)。疑問符・感嘆符は全角(？)を使い、感嘆符(！)は原則使わない。
- 括弧は全角(（）)。UI のボタン名・項目名の引用は「」。
- 進行中の表示は「…」(U+2026)。現状の `...` は置き換える。

## 2. 用語

AGENTS.md の用語ルール(エントリー / 当日受付 / 受付番号 / 成績照会)に加えて次を定める。

| 概念 | 採用 | 使わない |
|---|---|---|
| 運営への連絡先(参加者・採点者に案内するとき) | 運営 | 管理者(ロール名と紛らわしいため) |
| 権限ロール名 | 所有者 / 管理者 / 採点者 | 運営(ロールの意味では使わない) |
| メール差出人 | 「〇〇 実行委員会」 | — |
| Google 認証の操作 | ログイン | サインイン |
| メール確認の手順 | メール認証(手順名)/ 認証コード(6桁のコード) | 確認コード |
| エントリーを取りやめる操作 | キャンセル | 取消 |
| 当日受付を元に戻す運営操作 | 受付の取り消し(別概念。キャンセルと呼ばない) | — |
| 二次元コード | 二次元コード | QRコード / 2次元コード |

## 3. エラー文の型

| 状況 | 型 | 例 |
|---|---|---|
| 操作の失敗 | 「〜できませんでした。」+ 次の行動 | 認証コードを送信できませんでした。時間をおいて再度お試しください。 |
| 状態による不可 | 「〜できません。」+ 理由 | 当日受付済みのため、内容の変更はできません。 |
| 一時的な障害 | 「時間をおいて再度お試しください。」 | — |
| 入力の問題 | 「もう一度お試しください」ではなく、直す箇所を示す | メールアドレスの形式が正しくありません。 |
| 上限・制限 | 何の上限かを書く | 認証コードの送信回数が上限に達しました。10分ほど待ってからお試しください。 |

- 「失敗しました」は使わず「できませんでした」に寄せる。
- 「もう一度」は直前の操作をすぐやり直す場合。「時間をおいて再度」は障害・制限など待つ必要がある場合。
- 待機の言い回しは「時間をおいて」に統一する(「しばらく待って」「しばらくしてから」は使わない)。
- 原因が分かっているのに汎用文言に丸めない。特にサーバー応答(403 / 429 など)は画面に反映する。
- 内部エラー文(英語メッセージ・スタック・SQL 由来)を利用者に見せない。

## 4. 進め方

1. このガイドを承認する。
2. 文言一覧(全件)を作り、ガイドとの差分を付ける。
3. 参加者向け画面・メール → 管理画面の順に、ページ単位で小さく書き換える。
4. 各段階で `npm test`、JS 構文チェック、`git diff --check` を通す。

## 5. 実装で追加した決め事

- 技術的な詳細(`e.message` など)は、運営側の画面(管理画面・受付・採点)に限り、末尾に「（詳細：…）」の形で付けてよい。コロンも全角にする。参加者向けの画面では出さず、サーバーが返した日本語の `error` 文だけを表示する。
- 画面に出る日本語の文言に、半角の括弧・コロン・感嘆符を混ぜない。補足は全角の括弧（）、ラベルの区切りは全角のコロン（例: 「受付番号：012」「エントリー開始：…」）、感嘆符は全角（！）にする。半角のまま残してよいのは、書式そのもの(CSVの例 `問題番号,解答,別解`、`#大会名` のハッシュタグ、URL、コード)と、iPhone のコード候補が読み取る認証コードメールのプレーンテキストの1行(`認証コード: 123456`。動作確認済みのため変えない)だけ。
- 開発者向けのコンソールのログは対象外。
- メンバーを権限から外す操作は「外す」(状態は「外し済み」)に統一する。「キック」「停止」「削除」は使わない。
- 受付状態の拒否(受付停止・期間外・大会なし)は、汎用の 500 エラーに丸めず、状態が分かる文言を返す。
- 画面の文言を変えたら、該当 JS の `?v=` を上げる(キャッシュ更新)。

- トースト・ステータスなど「文」として出す短い通知も、句点（。）で終える。バッジやボタンのラベル（「完了」「未着手」など）は対象外。
- 感嘆符は使わない。ただし、参加者が SNS に投稿する共有文（`share_card.js` / `my.js` の「に参加しました！！」）は例外とする(ここも全角)。
- 運営ヘルプの画面名は実際の画面に合わせる（「参加者に共有するリンク」「答案の取り込み」など）。「要確認」は画面名どおりで、ヘルプでも「競合」とは書かない。

- Edge Function 呼び出しの失敗は、`supabase_api.js` の共通処理で日本語にそろえる。通信失敗は「サーバーに接続できませんでした。〜」、JSON でない応答は「処理を完了できませんでした。〜」。画面側で `Failed to fetch` や関数名つきの英語を出さない。
- 参加者向けの画面は、サーバーが返した日本語の `error` と、上記の共通メッセージだけを表示する。それ以外の例外は汎用の文言にして、詳細はコンソールにだけ残す。
- 「リセット」のように取り返しのつかない操作の確認文は、実際に消えるもの・残るものを列挙する(模範解答も消える)。確認文を変えたときは、削除対象のSQLと突き合わせる。

## 6. 「大会」と「プロジェクト」

- 参加者・採点者に見える文言(エントリー・マイエントリー・エントリーリスト・参加規約・Edge Function のエラー文)は「大会」。
- 運営の管理画面とヘルプでは、システム上の管理単位を指す「プロジェクト」(作成・リセット・退出など)をそのまま使う。
- 全画面を「大会」に統一するのは、影響が管理画面とヘルプの数十件に及ぶため見送り。やるなら別作業にする。
